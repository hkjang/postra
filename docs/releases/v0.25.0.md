# Postra v0.25.0 — 동기화 실패 진단, 일시적 실패 재시도, 보낸 메일 후속 작업

메일 동기화 실패는 이 서비스에서 가장 심각한 오류인데, 화면에는 "서비스 응답 시간이 초과되었습니다" 한 줄만 남았습니다. 그 문장은 어느 단계에서 멈췄는지, 서버에 닿기는 했는지, 정말 시간 초과였는지조차 말해 주지 않습니다. 이번 릴리즈는 실패한 동기화가 **멈춘 지점을 단계·유형·시간·재시도·연결 수로 기록**하게 하고, 일시적인 연결 실패는 다시 시도하며, 보낸 메일함 확인 결과까지 함께 남깁니다. 보낸 메일 쪽은 v0.24.0의 수집에서 한 걸음 더 나가 후속 작업(답장 대기, Bcc, 후속 메일 작성, Ask)을 지원합니다. **DB 마이그레이션 3건**(`messages.bcc_json`, `jobs.diagnostic_json`, 스레드 인덱스, 기동 시 자동)이 있고 새 필수 환경변수는 없습니다.

## 동기화 실패 진단

- 모든 인바운드 어댑터(POP3·IMAP)가 실패를 **단계**와 **유형**으로 분류합니다. 단계는 `policy`·`secret`·`host_check`(서버에 패킷을 보내기 전) → `tcp_connect` → `tls_handshake` → `greeting` → `starttls` → `login` → `select` → `enumerate` → `fetch`·`list`·`idle`·`logout`이고, 유형은 `timeout`·`refused`·`reset`·`closed`·`unreachable`·`dns_not_found`·`dns_failed`·`tls_certificate`·`tls_handshake`·`rejected`·`cancelled`·`config`·`other`입니다.
- 작업 화면(`/app/jobs`)에 **"멈춘 지점"**이 생겼습니다. 요약 문장과 함께 서버·명령·서버 응답 코드·소요 시간·그 단계의 제한 시간·연결 시도·이 서버에 유지 중인 연결 수·시작 전 대기가 보입니다. 장애 화면의 동기화 행 detail 에도 같은 요약이 들어갑니다. `GET /api/jobs`, `GET /api/jobs/{id}`, MCP `job_status` 는 같은 `diagnostic` 객체를 돌려줍니다.
- **"정말 시간 초과인가"를 구분합니다.** 그 단계의 소요 시간과 제한 시간을 함께 남기므로, 제한 시간을 다 쓴 진짜 무응답과 제한 시간이 남았는데 끊긴 경우(연결 제한 시간, 작업 취소, 프록시 유휴 종료 등 예산이 다른 곳에서 온 경우)가 구별됩니다. 후자는 "이 단계의 제한 시간에는 이르지 않았습니다"로 표시합니다.
- **동시 접속 제한이 보입니다.** 이 노드가 그 서버·그 계정에 유지 중인 인바운드 연결 수를 함께 기록합니다. IMAP 실시간 대기(IDLE)가 계정마다 하나를 계속 쓰기 때문에 `greeting` 단계의 `timeout`/`reset` 과 계정 연결 2개가 같이 보이면 서버의 계정별 동시 접속 허용 수를 먼저 확인하면 됩니다. 이전에는 이 상황이 단순한 시간 초과와 구별되지 않았습니다.
- 실패 메시지가 유형별로 갈라집니다(거부·끊김·주소 확인 실패·인증서·서버 거부·설정 중단). 장애 화면의 지문도 메시지로 만들어지므로, 시간 초과와 연결 거부가 한 행으로 합쳐지지 않습니다.
- 기록되는 값은 Postra 자신의 어휘 아니면 숫자입니다. 메일 서버 문장은 비밀번호나 메일 내용을 되돌려 줄 수 있으므로 **어디에도 남기지 않고**, RFC 5530/2449/3206 의 응답 코드만 남깁니다. 읽는 시점에 모든 필드를 닫힌 목록으로 다시 검사하고 요약을 그 필드로부터 다시 만들기 때문에, 다른 버전이나 다른 노드가 쓴 행도 같은 경계를 지납니다.
- 읽는 방법은 [동기화 실패 진단 문서](https://github.com/hkjang/postra/blob/v0.25.0/docs/SYNC_DIAGNOSTICS.md)에 단계·유형·조합별 확인 항목으로 정리했습니다.

## 일시적 실패를 실패로 만들지 않기

- 동기화는 **일시적인 연결 실패를 최대 3회까지 다시 시도합니다**(시간 초과, 연결 거부·끊김, 서버의 일시 거부 코드 `[IN-USE]`·`[LIMIT]`·`[LOGIN-DELAY]`·`[SYS/TEMP]`·`[UNAVAILABLE]`·`[THROTTLED]`). 잠깐 바쁜 서버나 동시 접속 한도에 걸린 연결이 곧바로 실패한 동기화가 되지 않습니다.
- 비밀번호 거부, 인증서 불신, 호스트 없음, 관리자 정책 차단은 다시 시도하지 않습니다. 같은 결과가 반복될 뿐입니다.
- 재시도로 성공한 동기화도 흔적을 남깁니다: "연결 시도 2회(이전 시도: 서버가 연결을 끊었습니다 — 재연결 후 진행)". 완전히 실패하기 전에 보이는 신호입니다.
- **서버의 일시 거부를 비밀번호 실패로 취급하지 않습니다.** 이전에는 로그인 단계의 모든 실패가 인증 실패였고, 그 계정은 `credential_error` 로 내려가 사람이 손대기 전까지 동기화되지 않았습니다. 이제 서버가 이 자격 증명을 거부한 경우에만 계정 상태를 바꿉니다.

## 가져오지 못한 메일을 성공으로 보고하지 않기

- 메일을 하나도 못 가져왔는데 작업이 "완료"로 끝나던 경우가 있었습니다. 본문 수신이 전부 실패하면 통계의 `failed` 만 올라가고 상태는 성공이었습니다 — 새 메일이 안 오는 이유가 화면에서 사라집니다.
- 이제 가져오려 한 메일이 **전부 실패하면 실패**, 일부만 실패하면 **일부 완료**(`partially_succeeded`)로 끝나고, 멈춘 단계(`fetch`)와 유형이 함께 기록됩니다. 일부 완료는 장애 화면에 경고로 남습니다.

## 보낸 메일함 패스

- 보낸 메일함 확인 결과가 진단에 남습니다: `synced`·`throttled`(실시간 동기화에서 생략)·`none`(서버에 없음)·`failed`(단계·유형 포함). 실패해도 받은 메일 동기화는 그대로 성공합니다.
- **실시간 동기화는 보낸 메일함을 10분에 한 번만 읽습니다.** IDLE 은 받은편지함만 알려 주므로 새 메일마다 보낸 메일함을 다시 열 이유가 없고, 큰 보낸 메일함에서는 그 열거 작업이 실시간 동기화 비용을 두 배로 만들었습니다. 주기적·수동 동기화는 항상 읽습니다.

## 보낸 메일 후속 작업

- **답장 대기 보기**: 보낸 메일 중 아직 아무도 답하지 않은 것(대화의 마지막 메시지가 내 메일인 것)만 봅니다. 검색 API `folder=sent&awaiting_reply=true`, MCP `mail_sent_search(awaiting_reply=true)` 도 같습니다. 상대가 답할 의무가 있다는 뜻은 아니며 대화의 마지막 발화자만 판단합니다.
- 사이드바에 **보낸메일**이 받은메일과 같은 보기로 들어갔고, 기존 `/sent` 는 발송 상태(큐·재시도·결과)를 보는 **발송 현황**으로 이름을 정리했습니다.
- **Bcc**: Postra 가 보관하는 발송 사본과 서버 보낸 메일함 사본의 Bcc 수신자를 기록하고 소유자에게만 보여 줍니다. 전송된 바이트에는 Bcc 헤더가 들어가지 않습니다 — 수신자가 숨은 참조를 알게 되면 안 됩니다.
- 보낸 메일에서 답장을 누르면 **같은 사람들에게 보내는 후속 메일**이 됩니다(자기 자신에게 쓰는 메일이 아닙니다). 전체 답장은 원래 Cc 를 유지하고 Bcc 는 넣지 않습니다. 보낸 메일에는 스마트 답장 대신 후속 메일 작성을 제안합니다.
- **Ask Postra** 가 보낸 메일을 근거로 씁니다. "내가 답장했나", "보낸 메일 중 …" 같은 질문에는 보낸 메일 자리를 따로 확보해 받은편지함이 밀어내지 못하게 하고, 근거마다 받은/보낸 구분과 수신자를 함께 넘깁니다. 벡터 색인은 계속 받은 메일만 다룹니다.

## SSO 계정 연결

- 신원 공급자가 이메일을 **검증되지 않았다고 명시**한 경우 그 이메일로 기존 로컬 계정을 연결하지 않습니다. 사용자가 자기 이메일을 스스로 바꿀 수 있는 환경에서 남의 계정을 가져가는 경로였습니다. 클레임을 아예 보내지 않는 공급자는 이전과 같이 동작합니다.

## 검증

- 전체 Go race 테스트, Go vet, `gofmt`, canonical API 계약 검사
- 진단: 멈춘 단계·유형·소요/제한 시간·연결 수 기록, 장애 행 detail 전달, 서버 문장·주소 미포함 확인
- 재시도: 일시적 끊김 후 2회차 성공과 그 기록, 비밀번호 거부는 1회로 중단하고 계정을 `credential_error` 로, 서버 일시 거부(`[IN-USE]`)는 재시도하고 계정 상태 유지
- 본문 수신 전부 실패 → 실패, 일부 실패 → 일부 완료, 각 경우의 단계 기록
- 보낸 메일함: 정상·없음·거부 3가지 결과와 받은 메일 동기화 성공, IDLE 동기화의 생략 기록
- 설정 단계 중단(`policy`)이 서버 문제로 읽히지 않음, 제한 시간이 남은 중단과 소진된 중단의 구분
- 읽기 경계: 알 수 없는 단계·유형·코드·호스트·요약을 모두 버리고 검증된 필드로 요약을 다시 생성, 숫자만 있는 진단은 표시하지 않음
- 인바운드 연결 수 집계(호스트·계정별 증감), 재시도 대상 분류 8종
- React 49개 파일·414개 테스트, TypeScript 검사, 배포 자산 재빌드. 작업 화면의 진단 표시, 일부 완료 표기, 진단 없는 작업, 성공 작업의 진단, 형식이 어긋난 진단 거부

테스트는 로컬 모의 메일·AI 서비스를 사용하며 운영 메일 서버에 접속하거나 운영 데이터를 변경하지 않습니다.

## 업그레이드 및 호환성 주의사항

v0.24.0에서 새 설정 키·새 필수 환경변수는 없습니다. 기동 시 `messages.bcc_json`, `jobs.diagnostic_json` 컬럼과 `messages(user_id, thread_id, date)` 인덱스가 자동 추가됩니다(SQLite·PostgreSQL, 기존 데이터 변경 없음). DB·SecretStore·ObjectStore·KEK를 백업하고 유지한 상태에서 실행 파일 또는 컨테이너 이미지를 교체한 뒤 재시작하세요. Go 단일 실행 파일에 React 자산·글꼴을 포함하므로 폐쇄망 런타임에 Node 서버나 외부 CDN이 필요하지 않습니다.

- 동기화 작업 응답에 `diagnostic` 객체가 추가됩니다. 작업 JSON을 엄격하게 파싱하는 자동화가 있다면 확인하세요.
- 이전에 "완료"로 끝났던 일부 동기화가 이제 **실패 또는 일부 완료**로 보일 수 있습니다. 새 실패가 아니라 가져오지 못한 메일이 드러난 것입니다. 장애 화면에 동기화 행이 늘어날 수 있으며, 실패 유형별로 행이 분리됩니다.
- 로그인 단계의 일시적 서버 거부는 더 이상 계정을 `credential_error` 로 내리지 않습니다. 이 상태로 멈춰 있던 계정은 비밀번호를 확인한 뒤 계정 상태를 다시 활성으로 바꾸면 동기화가 재개됩니다.
- 실시간 동기화는 보낸 메일함을 10분 간격으로 읽습니다. 보낸 메일이 즉시 보여야 하는 운영이라면 자동 동기화 주기(`sync.auto_sync_minutes`)를 함께 확인하세요.
- 사이드바의 `/sent`(발송 현황)와 새 보낸메일 보기(`/mail?folder=sent`)는 다른 화면입니다. 북마크가 있다면 확인하세요.
- 검증되지 않은 이메일로 기존 로컬 계정에 연결되던 SSO 로그인은 이제 거부됩니다. 해당 계정은 관리자가 사용자 이메일을 확인해 정리하거나 공급자에서 이메일 검증을 켜세요.
